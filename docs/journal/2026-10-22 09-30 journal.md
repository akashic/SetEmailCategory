# Journal — 2026-10-22

## Session — 09:30

**Summary:** The task was to update the Phase 4 (first deployment) scripts and runbook for two networking requirements. First, a William Buck policy rule: every subnet must have a network security group. Second, an existing subnet is to be re-used, so the template and scripts must accept a subnet's details instead of always creating one. The work covered the Bicep templates, the OIDC setup script, a new pre-deployment check script, the deploy workflow and the deployment documentation.

**Discussion & decisions:** Private networking needs two subnets: an app-integration subnet delegated to `Microsoft.App/environments`, and a private-endpoint subnet, which can't be delegated. The request didn't say which of these already exists, so the user was asked before any design was fixed. The user also asked to be consulted on any other uncertainty. The questions and answers:

- *Which subnet is being re-used?* **Support either or both.** The template takes two optional IDs and creates a VNet only for the subnets that aren't supplied.
- *Where does the existing subnet live relative to the deployment RG?* **Not sure yet.** So the script grants access whenever a supplied resource is outside the RG, and skips the grant when it's inside.
- *Which NSG should the template attach to the subnets it creates?* **Either.** It uses `existingNsgId` if that's set; otherwise it creates one NSG per subnet with Azure's default rules only.
- *How strict should the checks on an existing subnet be?* **The script checks and fails fast.** It lists every problem, then stops before anything is changed.
- *If only one subnet is supplied, the other ends up in a new VNet. How should that be handled?* **Allow it and document the peering.**
- *What role should the deployment identity get on an existing subnet outside the RG?* **Network Contributor, scoped to the subnet.**

The Flex Consumption subnet rules were checked on Microsoft Learn, following the repo's own lesson to verify volatile platform facts there. The app subnet must be delegated only to `Microsoft.App/environments`, be at least /27, be in the app's region, and have no private or service endpoints. The same research found that linking a private DNS zone to a VNet needs `virtualNetworks/join/action` on the whole VNet. So when the app subnet is outside the RG and the template creates the DNS zones, Network Contributor goes on that subnet's VNet, which is wider than the subnet-only scope the user chose. That deviation is documented, and it can be avoided with central DNS (`createPrivateDnsZones = false`). The template creates subnets inline in the VNet so each one has its NSG at creation, which is when a "deny subnet without NSG" policy evaluates it. The DNS zones are now linked to the app subnet's VNet, because that's where the app resolves storage names from.
