## The problem

We have Power Automate flows that need to put Outlook categories on emails in a **shared mailbox**. The built-in Office 365 Outlook connector can't do that for shared mailboxes. The plan is a small Azure Function that calls Microsoft Graph, exposed to Power Platform through a custom connector. It has to be deployable into a corporate tenant with as little hand-cranking as possible.

## 15:10: Language and hosting decision

I went with **C# / .NET 10 isolated worker on the Flex Consumption plan**.

Reasoning:
- **Reliability over raw speed.** For one Graph call per request, the performance differences between runtimes are noise. What matters is strong typing, first-party Azure.Identity support, and long support windows. .NET 10 is LTS until November 2028.
- **I checked against Learn that Flex Consumption supports .NET 10 isolated** (runtime version string `'10.0'`). Flex was preferred because it has scale-to-zero, VNet support, "always ready" instances, and is Linux-only, which suits us. Linux Consumption is retiring in 2028 anyway.
- **PowerShell was considered** because ops teams can read it, but rejected: it's the slowest to cold-start and the weakest at error handling.
- .NET 10 SDK 10.0.101 was already installed locally.

Then I asked four design questions. The answers:

| Question | Answer | Consequence |
|---|---|---|
| Caller auth | Entra ID + custom connector | Easy Auth on the function. Two app registrations: the API and the connector client. |
| Networking | Not sure yet | Parameterise private networking as a toggle and leave it off. |
| Pipeline | GitHub Actions | OIDC federated credential, no stored secrets. |
| Mailboxes | Single, fixed | Mailbox address in app settings, not in the request. |

## 15:12: Research before writing infra

I pulled the facts most likely to have drifted from Learn, rather than relying on memory:

- **Exchange RBAC for Applications.** This is the key security piece. It replaces Application Access Policies. The important gotcha, straight from the FAQ: RBAC-for-Apps grants are a **union** with Entra ID grants. If the managed identity also has `Mail.ReadWrite` consented in Entra, the mailbox scope is meaningless. So the design is that the identity gets **no** Graph permission in Entra, only an Exchange role assignment (`Application Mail.ReadWrite`) with a management scope covering one mailbox. Changes take 30 minutes to 2 hours to propagate.
- **Easy Auth works on Flex Consumption.** The migration docs talk about recreating it, so it's supported.
- **Flex Bicep shape.** I fetched Microsoft's `azure-functions-flex-consumption-samples` and `functions-quickstart-dotnet-azd` from GitHub for the `functionAppConfig` structure, identity-based `AzureWebJobsStorage__*` settings, `APPLICATIONINSIGHTS_AUTHENTICATION_STRING=Authorization=AAD`, and the role set: Blob Data Owner, Queue and Table Data Contributor, and Monitoring Metrics Publisher.
- **Flex deploys use OIDC or Entra.** SCM basic auth doesn't apply, so `az functionapp deployment source config-zip` after `azure/login` is the documented path.

## 15:15: Function implementation

I scaffolded with `func init --worker-runtime dotnet-isolated --target-framework net10.0`. The template now defaults to OpenTelemetry with the Azure Monitor exporter, which I kept.

**Decision: no Graph SDK.** The Microsoft.Graph package is tens of MB and hurts cold start for what is two REST calls (GET and PATCH). I used `HttpClient`, an `Azure.Identity` token handler, and `Microsoft.Extensions.Http.Resilience` for retries.

The shape of the code:
- `POST /api/messages/categories` takes `{ messageId | internetMessageId, categories[], mode: add|replace|remove }`.
- **Idempotent.** Add or remove compares the result with what's there and skips the PATCH if nothing changes (`changed: false`).
- **Optimistic concurrency.** GET returns `@odata.etag`, and the PATCH sends `If-Match`. On 412 it re-reads and retries, up to 3 times. Two flows touching the same new email at once is plausible.
- **Validation:**
  - Trim category names and de-duplicate them case-insensitively.
  - **Reject commas.** Outlook treats them as separators, and a comma almost always means the flow author passed `"A, B"` as one item.
  - Cap at 25 categories of 255 characters each.
  - An empty list is only allowed with `replace`, which clears all categories.
- **Errors are RFC 7807 ProblemDetails**, carrying Graph's `request-id` for support tickets:
  - 404 when the message isn't found.
  - 409 when the internet message ID is ambiguous.
  - 502 when the function's identity lacks access, because that's our misconfiguration, not the caller's fault.
  - 503 for transient failures.
- **Auth.** The trigger is `AuthorizationLevel.Anonymous` because Easy Auth sits in front. As defence in depth, the function rejects requests that have no `X-MS-CLIENT-PRINCIPAL-ID` header. The platform injects that header after validating the token and strips it from client requests.
- **Credential.** `ManagedIdentityCredential(SystemAssigned)` explicitly in Azure, which is deterministic with no probing. `DefaultAzureCredential` locally.
- **Telemetry.** App Insights has local auth disabled, so the OTel exporter is given the same Entra credential. Later I turned on `IncludeScopes` so the caller ID and correlation ID land in `customDimensions` for audit queries.
- **`/api/health`** is anonymous (excluded from Easy Auth) and returns only the version. The version includes the git SHA, which the pipeline uses to confirm the new build is live.

**Bug caught while running locally:** a token failure (`AuthenticationFailedException`) escaped as an unhandled 500. I mapped it to the 502 "can't access mailbox" path.

**Tests:** xUnit with a scripted fake `HttpMessageHandler` covering merge logic, the 412 retry loop, error mapping, internet message ID lookup with OData quote escaping, and function-level auth and status mapping. One test failed at first only because records with list members compare by reference. I fixed the test, not the code. **38 tests passing.**

I also ran `func start` locally against the real host to check routes, the 401 guard, validation, and the token-failure mapping end to end.

## 15:20: Infrastructure (Bicep)

**Decision: native resources, not Azure Verified Modules.** It's more code, but everything is visible to a security reviewer, and the pipeline doesn't need to reach the public Bicep registry. Locked-down corporate runners often can't.

- **Scope:** `resourceGroup`. In corporate tenants the platform team usually owns RG creation and policy.
- **Modules:**
  - `monitoring.bicep`: Log Analytics and App Insights with `DisableLocalAuth`.
  - `storage.bicep`: no shared keys, no public blobs, TLS 1.2. Private endpoints and DNS zones are optional.
  - `network.bicep`: only deployed when private networking is on. Has a subnet delegated to `Microsoft.App/environments`.
  - `functionApp.bicep`: the FC1 plan, the site, Easy Auth (`authsettingsV2`), FTP and SCM basic auth disabled, diagnostic settings, and role assignments.
  - `alerts.bicep`: optional. Sends an email on failed requests.
- **Easy Auth configuration:**
  - The issuer is the v2.0 endpoint; the API app is set to issue v2 tokens.
  - Allowed audiences are both the client ID and `api://` plus the client ID.
  - `allowedApplications` is the connector client only. Tokens issued to any other app are rejected before our code runs.
- **Private networking toggle:** storage behind private endpoints plus outbound VNet integration. **Inbound stays public**, because Power Platform's cloud connectors have to reach it. There's a `createPrivateDnsZones` switch for landing zones where Azure Policy manages `privatelink.*` zones centrally.
- **Initial scale:** I set max instances to **2** with 2 concurrent requests per instance, to stay under Graph's 4-concurrent-requests-per-mailbox limit. *This turned out to be wrong; see 16:15.*

`az bicep build` and `lint` came out clean.

## 15:22: Admin scripts, connector, pipeline, docs

**Scripts are PowerShell 7** so they run unchanged in Azure Cloud Shell. All of them are idempotent.
- `Setup-EntraApps.ps1`:
  - Creates the API and connector app registrations through `az rest` against Graph.
  - Gives the scope a stable GUID, derived from an MD5 of `workload/env/user_impersonation`, so re-runs never create duplicates.
  - Optional assignment-required group on the API.
  - Admin consent through `oauth2PermissionGrants`.
  - A client secret that's printed once and never written to disk.
  - Adds the connector's unique redirect URI on a second run.
- `Setup-GitHubOidc.ps1`:
  - A user-assigned identity with a federated credential for `repo:<repo>:environment:<env>`.
  - **Contributor** on the RG, plus **RBAC Administrator constrained by an ABAC condition**. It can only assign the four data roles the app needs, and only to service principals. That's the least privilege that still lets Bicep create the role assignments.
- `Grant-MailboxAccess.ps1`:
  - **Refuses to run if the managed identity has any Graph app permission in Entra**, because of the union gotcha above.
  - Then runs `New-ServicePrincipal`, `New-ManagementScope` (filtered on primary SMTP address), and `New-ManagementRoleAssignment`.
  - Proves the result with `Test-ServicePrincipalAuthorization`, including a negative-test mailbox.
- `Build-ConnectorDefinition.ps1` fills the swagger and `apiProperties.json` templates per environment.

**Script checking.** The local `pwsh` was broken, so I installed PowerShell 7.6.6 as a .NET global tool in the scratchpad, just to parse-check and run PSScriptAnalyzer. That found two things:
- Using `$args` as a variable name. It's an automatic variable in PowerShell; renamed.
- **A real bug:** calling `$PSCmdlet.ShouldProcess` inside a non-advanced function, where `$PSCmdlet` is null. Fixed with `[CmdletBinding(SupportsShouldProcess)]`.

Later I hardened the Exchange lookups too: some EXO cmdlets throw terminating errors on "not found" regardless of `-ErrorAction`, and Exchange can normalise scope filter text.

**Workflow** (`.github/workflows/deploy.yml`):
- On a PR: build and test, a ReadyToRun publish for `linux-x64`, and a Bicep lint.
- On `main` or manual dispatch, additionally: `what-if`, deploy the Bicep, run `config-zip`, then the smoke test. The smoke test waits for the health version to contain the commit SHA, then checks that an unauthenticated POST returns 401.
- **I checked the latest action versions with `gh api` rather than guessing:** checkout v7, setup-dotnet v6, upload-artifact v7, download-artifact v8, azure/login v3.

## 15:45: External review, round 1

Another agent reviewed the code. I assessed each point on its merits.

**Accepted:**
- **Empty PATCH response.** The reviewer guessed at a null dereference in replace mode. Looking at it properly, the real bug was worse: `PatchCategoriesAsync` returned `null` for both a **412** and a **successful empty-body response**. Add or remove mode would treat a successful write as a conflict, re-read, see nothing to change, and report `changed: false`. Fixed so that `null` means 412 only.
- **Fail closed if Easy Auth is ever disabled.** Without Easy Auth the platform no longer strips the principal headers, so the header check could be forged. Added a check on `WEBSITE_AUTH_ENABLED`; if it isn't `True` in Azure, every request is refused.
  - **Uncertainty:** the variable is documented for App Service but not explicitly for Flex. I put the check behind `Security__RequireEasyAuthEnabled`.
  - I picked 500 "so retry policies don't hammer it". *That reasoning was wrong; see 16:15.*
- **Normalise `internetMessageId`.** Graph stores it with angle brackets, so the function adds them if they're missing.
- **`global.json`** pinning SDK major version 10 (`rollForward: latestFeature`).
  - The Homebrew SDK switch earlier showed how easily the toolchain can change underneath us.
  - I *didn't* point setup-dotnet at the file, because it may install exactly 10.0.100, without security patches. CI uses `10.0.x`, and `global.json` still enforces the major version.

**Rejected, with reasons:**
- *"Preview .NET risk":* .NET 10 is GA LTS, and I'd already verified Flex supports it.
- *"Validation messages mask each other":* they don't. That message only appears when there are no other errors.
- *"No CI found":* the reviewer couldn't see `.github`.
- *Token per request:* Azure.Identity caches tokens.
- *`MaxIdLength` and `MaxConcurrencyAttempts`:* not worth tuning.
- *Graph 403 vs Easy Auth 403:* they can't be confused, because Easy Auth rejects before our code runs.

## 16:10: Self-review, round 2

The user asked for an aggressive review against the real caller: **a polling shared-mailbox trigger calling through a custom connector.** That framing exposed things a generic review missed. I verified the platform facts on Learn before acting on them:
- Power Automate's synchronous request timeout is **120 s**.
- The default retry policy is **12 retries over about an hour** on the Medium/High profiles and **only 2** on Low.
- Flex docs say **max instances below 40 "can cause frequent request failures"** for HTTP apps.
- Graph's Outlook limit is **4 concurrent requests per app per mailbox**.

Findings and fixes:

1. **Bursts rejected at the platform.** My 2×2 instance cap meant that 30 emails arriving together would mostly get platform 429s before reaching the code. That was a bad trade.
   - Fix: max instances 40, per-instance concurrency 16, and a **process-wide `SemaphoreSlim(4)` handler** gating Graph calls.
   - The gate is placed innermost, so a slot isn't held during retry back-off.
   - Graph 429s caused by multiple instances are retried with `Retry-After`.
2. **Worst-case run time of about 7 minutes**, from up to 7 sequential Graph calls at up to 60 seconds each, against Power Automate's 120-second limit. Power Automate would time out and retry while the first invocation was still running, and the duplicates would then fight over the 4 Graph slots.
   - Fix: a **90-second per-invocation deadline** (configurable, 10–110 s) through a linked CTS, returning 503 "Timed out".
3. **Moved messages.** Message IDs change when a message moves between folders. The trigger polls, so a person or an inbox rule can easily move the message first. And when `messageId` was present, `internetMessageId` was ignored.
   - Fix: fall back to the internet message ID on 404 or an invalid-ID error.
   - The runbook now says to **always pass both**, and the connector shows both fields prominently.
   - This also covers my unverified assumption about the trigger's ID format.
4. **Connection identity** (operational). Delegated connections break on a password reset, when the owner leaves, under Conditional Access sign-in frequency, or after 90 idle days.
   - Probably the most likely failure in production, and it isn't a code problem.
   - The runbook now recommends a service account and Conditional Access exclusions agreed with the identity team.
5. **Unverified environment variables on Flex.** If `WEBSITE_AUTH_ENABLED` is missing, the fail-closed check returns 500 on every call, which is an outage. If `WEBSITE_INSTANCE_ID` is missing, the check is silently off.
   - Fix: detect Azure with any of `WEBSITE_INSTANCE_ID`, `CONTAINER_NAME` or `WEBSITE_SKU`.
   - `/api/health` now reports `runningInAzure` and `acceptingRequests`, and **the smoke test asserts both**, so this gets caught at deploy time instead of in production.
6. **Weak ETags and `If-Match`.** RFC 7232 says weak ETags never match `If-Match`. Graph documents `If-Match` for Outlook notes, not for messages.
   - Fix: the code corrects itself. If we get a 412 but the re-read ETag is unchanged, `If-Match` isn't usable, so it's dropped with a warning in the log.
7. **Error classification.**
   - Exchange's **409** (`ErrorIrresolvableConflict`) is now retried in all modes. Previously, replace mode threw `InvalidOperationException`.
   - Non-transient Graph 4xx responses now return **400 instead of 503**, so Power Automate doesn't retry a permanent error for an hour.
8. **Unhandled exceptions.**
   - A catch-all now returns ProblemDetails 500 and logs the error.
   - The Graph models are null-safe, because System.Text.Json assigns an explicit null over property initialisers.
   - Cancellation propagates to the function, which owns the deadline.
9. **My own comment was wrong.** Power Automate retries **every** 5xx, so "500 avoids retries" was false. That's actually fine (502 retries suit the RBAC propagation window), but the comment and README are now corrected, and the runbook gives an explicit retry policy.
10. **Circuit breaker removed.** I replaced the standard resilience handler with retry and timeouts only. Graph's `Retry-After` already does the breaker's job, and with bursts of 429s the breaker would fast-fail requests.

Deliberately not done: accepting a string for `categories` (optional, and the user didn't take it up), and the Sent Items + Inbox duplicate case (rare, and it returns a clear 409).

**Testability refactor:** I moved the HTTP pipeline into `GraphClientRegistration.AddGraphClient()`. A new test builds the real DI pipeline with only the network faked, and proves a 429 is retried with the bearer token on every attempt. One test initially failed because the fake handler ignored cancellation tokens. I fixed the fake to behave like a real handler.

Committed as `afa3f46`. **87 tests.** Lint is clean, and a local host run was verified.
