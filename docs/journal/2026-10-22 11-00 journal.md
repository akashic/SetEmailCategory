**Discussion & decisions:**
- **Merge blocked earlier.** Before this session's changes, merging PR #13 with `gh pr merge` was denied by Claude Code's permission check ("Merge Without Review"). It wasn't worked around: the user was given the command to run instead, or the option of adding a permission rule. While checking the PR, it turned out `build-and-deploy` is disabled on `akashic/SetEmailCategory`, so the PR only had CodeQL checks (all passing) and no build check.
- **Manual-only deployment.** The user asked for the deploy workflow not to run on push. The `push` trigger was removed, and the deploy job now runs only when started from *Run workflow*. The `pull_request` trigger was kept, because it runs only the build and tests, and branch protection (setup guide section 5.3) requires that `build` check. So "only run manually" was read as applying to deployment, not to PR builds.
- **Same VNet.** The user said all resources are in the same VNet. Two clarifying questions established that **both** subnets (app and private endpoint) already exist in that VNet, and that it's **platform-managed, in another resource group**. The alternative, creating the missing subnet inside the existing VNet, would have needed template changes and write rights on the platform's VNet. Consequences:
  - the template creates no VNet, subnets or NSGs
  - no peering or IP ranges are needed
  - the VNet is shared, so `createPrivateDnsZones` must be `false`
  - private DNS (N2) is now the main blocker: until the hub zones or a registering policy are confirmed, the app can't resolve storage
- **Placeholders.** The two subnet IDs went into `prod.bicepparam` as `'<...>'` placeholders rather than commented-out lines. That way the deploy job's placeholder check stops a deployment until they're filled in, the same way it already does for the mailbox and app IDs.
